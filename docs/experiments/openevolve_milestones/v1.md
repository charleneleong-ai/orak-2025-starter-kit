# OpenEvolve v1 + v2 — pokemon milestone library spike

> **TL;DR**: v1 (300 steps) showed the milestone library can't be improved
> by scaffold-search alone. v2 (600 steps) lifted baseline 4/7 → 5/7. v3
> (1200 steps single baseline) lifted further to **6/7**. v4 (2000 steps
> single baseline) **regressed to 5/7** — confirming run-to-run variance is
> substantial and "each doubling buys one milestone" is a noisy heuristic,
> not a deterministic law. **Verdict: land `max_steps: 1200` as production
> default; openevolve-on-scaffold is exhausted; cross-game pathology guards
> in the [TGAER MVA roadmap](../../generalized-agent-mva.md) are the right next bet.**



## Hypothesis

LLM-guided evolutionary search (OpenEvolve) over `_POKEMON_MILESTONE_LIBRARY` can
discover scaffold variants that beat the Stage S v2 baseline (`final_score=4/7`,
`map=OaksLab`) without manual scaffold iteration. This sidesteps the GSPO
zero-variance reroll wall by:

1. Operating on the surface where v1→v2 lift actually came from (subgoal + bridge
   edits, not weight updates).
2. Preserving diverse candidates via MAP-Elites (no group-variance blocker).
3. Using Gemini 2.5 Pro as the mutation LLM — distinct from the Gemma agent that
   serves rollouts, so search-LLM intelligence isn't bottlenecked by agent-LLM
   capacity.

## Three LLM roles (Gemini ≠ agent)

This experiment uses three distinct LLMs with non-overlapping roles. Worth pinning up-front because "Gemini" can otherwise be confused with the agent that actually plays pokemon.

| LLM | role | model | what it does | cost |
|---|---|---|---|---|
| **Agent LLM** | plays the actual game | **Gemma-4-26B-A4B-it** (AWQ-Int4) via vLLM @ `:8000` | The MACLA agent calling `move_to()`, `interact_with_object()`, etc. — tile-by-tile pokemon execution. *Not* Gemini. | local GPU only |
| **Mutation LLM** | proposes scaffold edits | **Gemini 2.5 Pro (70%) + Flash (30%)** ensemble | Reads `_POKEMON_MILESTONE_LIBRARY` source, emits SEARCH/REPLACE diff blocks to mutate it. "What if M6 also required ViridianMart? What if we added an M8?" | ~$3 over v1+v2 |
| **Evaluator LLM** | summarizes artifacts for the evolution loop | **Gemini 2.5 Flash** | Reads our evaluator's JSON artifacts (final_map, inference_calls, tokens, stderr_tail) and summarizes for openevolve's MAP-Elites selector. | included in ~$3 |

**Why this matters for the verdict:** mutation intelligence (Gemini 2.5 Pro) is *stronger than* agent intelligence (Gemma 26B). The whole experiment is intentionally two-tier so a winning mutation would represent a smarter LLM's structural insight that the smaller agent then executes. The negative result ("scaffold-search exhausted") therefore says something stronger than "Gemma can't find better scaffolds" — it says **even a smarter model's edits can't lift Gemma's behaviour, so the bottleneck isn't scaffold quality.** Evidence pointed at step budget + procedure-cache pathologies instead.

**Why Gemini specifically (vs Claude / GPT-4):** openevolve uses `openai.OpenAI()` under the hood, Google's Gemini API has an [OpenAI-compatible endpoint](https://generativelanguage.googleapis.com/v1beta/openai/) so the swap is config-only. `GEMINI_API_KEY` was already available from prior LangGraph + Gemini work, free-tier is generous, and Gemini 2.5 Pro's code-edit quality is comparable to Claude Sonnet at lower per-token cost.

**Gemini quirk worth flagging:** ~30-40% of mutation attempts emitted **non-SEARCH/REPLACE format** (markdown code blocks instead of openevolve's expected diff syntax). These errored at the diff-parsing step before any rollout was spawned — wasted ~5min of Gemini API time per failure. v1 errored on iters 2/4/8/11; v2 on 2/5/9/10. Not enough to invalidate the verdict (sample size still adequate) but worth knowing if anyone reuses the harness — stricter system prompt or a Claude/GPT-4 mutation model might have a higher format-success rate.

## Config

OpenEvolve loop knobs (full file: `experiments/openevolve_milestones/config.yaml`):

```yaml
max_iterations: 12        # ~7-8h overnight at parallel=2
population_size: 12       # small frontier; pop > iters would over-allocate
num_islands: 2            # cross-pollination, kept small to match iter budget
parallel_evaluations: 2   # vLLM continuous-batching → GPU ~30% util vs 0%
target_score: 0.95        # early-stop if a 6.65/7 candidate lands

llm:
  models:
    - {name: "gemini-2.5-pro",   weight: 0.7}
    - {name: "gemini-2.5-flash", weight: 0.3}
  evaluator_models:
    - {name: "gemini-2.5-flash", weight: 1.0}
```

Evaluator (`experiments/openevolve_milestones/evaluator.py`):
- One 300-step pokemon rollout per candidate, score = `final_score / 7`
- Hot-swaps the candidate library via `POKEMON_MILESTONE_LIBRARY_PATH` env var
- Returns rich artifacts (`final_map`, `inference_calls`, `elapsed_s`) so the
  mutation LLM has signal beyond raw score

## Verdict

**Hypothesis falsified.** All 9 valid candidates scored identically (4/7) and ended in the same map (Route1). The mutations were real — Gemini did make structural edits (different descriptions, threshold tweaks, ordering changes — visible by following `parent_id` chains where iters 7/9/10/12 mutated from previously-mutated candidates, not just the baseline) — but agent behavior was indistinguishable across the population.

**Why this is a clean signal**: zero variance + identical final map means the constraint isn't the scaffold the LLM is editing. The agent reliably reaches M4 (got starter), walks into Route1, then exhausts its 300-step budget before crossing into Viridian.

**The bottleneck is two layers down from the milestone library:**
1. **Step budget** — 300 steps is tight for a fresh-cache agent. Stage S v2's hand-tuned runs needed checkpoint resume + warm caches to reach M5.
2. **Planner execution** — even with the correct milestone declaring `requires_location="ViridianCity"`, the planner can't translate "go to Viridian" into an efficient sequence of `move_to(x, y)` calls within budget. The Stage Q exit-tile hint was the right band-aid but it's not enough.

Errored iters (Gemini malformed diff, no rollout): 2, 5, 9, 10.

### v2 verdict

**Two layered findings, stacked:**

1. **Step budget WAS a real constraint** at M5. Same scaffold + 600 steps → baseline lifted from 4/7 to **5/7** (+14.3pp). This part of the v1 hypothesis was right: 300 steps weren't enough.
2. **Mutations remain exhausted on this surface.** Across v1 (9 valid) + v2 (8 valid) = 17 rollouts. **None beat the time-adjusted baseline.** The 4 candidates that reached 5/7 only tied it; 2 regressed to 4/7.

**The remaining M6+ ceiling is planner-bound, not scaffold-bound.** Even with 600 steps and 4 candidates clearing M5, zero candidates crossed into ViridianMart (M6). The agent reaches ViridianCity then exhausts its remaining ~200-step budget unable to translate "navigate to ViridianMart" into the right `move_to(x, y)` sequence.

### Bonus signal: Gemini's M8 prediction

The "best" program OpenEvolve picked tied baseline at 5/7 but proposed a new
M8 milestone (`GetPokedexAndBalls` at `OaksLab`) — predicting that after M7
(DeliverOaksParcel) the game gives you the Pokedex + 5 Poké Balls in Oak's
Lab dialogue. The agent never reached M8 (capped at 5/7), so this never
contributed score. But Gemini correctly predicted a game milestone purely
from the milestone library's structure + descriptions — non-trivial planning
inference from the mutation LLM. If we extend to higher step budgets, this
M8 declaration could become useful.

## v3 — 1200-step step-budget probe (2026-05-23)

Single baseline rollout (no openevolve, no mutations), Stage S v2 scaffold,
`max_steps: 600 → 1200`. Launched 17:18 UTC, finished 20:15 UTC (177 min).

| run | score | raw | final_map | maps visited | tokens |
|---|---|---|---|---|---|
| `step_budget_1200_baseline` | 0.8571 | **6/7** | ViridianCity | OaksLab → PalletTown → Route1 → ViridianCity → **ViridianMart** → ViridianPokecenter | 6.02M |

### v3 verdict

**Step budget was the constraint at M5 AND M6.** Doubling steps lifted the
baseline 5/7 → **6/7** (+14.3pp). The agent walked into ViridianMart and
picked up Oak's Parcel cleanly. M7 (DeliverOaksParcel at OaksLab) didn't
fire — the agent ran out of steps on the return trip, ending in ViridianCity.

**Stage S series progression (same scaffold, just step budget varies):**

| max_steps | baseline score | final_map | gain |
|---|---|---|---|
| 300 (v1) | 4/7 | Route1 | — |
| 600 (v2) | 5/7 | ViridianCity | +14.3pp |
| 1200 (v3) | **6/7** | ViridianCity (post-Mart) | +14.3pp |

Linear. Each step doubling buys exactly one milestone. M7 likely needs another
~600-1500 steps for the return leg, but the per-iter cost climbs proportionally
(177 min/iter at 1200 steps → ~4-5h/iter at 2000+).

## v4 — 2000-step extension probe (2026-05-23/24)

Single baseline rollout at `max_steps: 2000`, same scaffold. Launched 21:02 UTC May 23, finished ~01:45 UTC May 24 (~4h45min).

| run | score | raw | final_map | tokens | notes |
|---|---|---|---|---|---|
| `step_budget_2000_baseline` | 0.7143 | **5/7** | ViridianCity | 10.2M | spent most of run looping in ViridianCity escape-valve mode (stagnation=1290 at step 1821) |

### v4 verdict — variance is real

**v4 regressed to 5/7 despite 2000 steps** vs v3's 6/7 @ 1200 steps. Same scaffold, same agent, same vLLM, just different run. This forces a revision of v3's "linear: each step doubling buys one milestone" story:

- **Run-to-run variance is substantial.** v3 (1200 → 6/7) and v4 (2000 → 5/7) bracket a real noise band — the agent's path through ViridianCity is stochastic, sometimes finds Mart entrance, sometimes doesn't.
- **More steps ≠ better.** v4 had 800 more steps than v3 and scored lower. The 2000-step budget mostly went into ViridianCity loops, not productive exploration.
- **Step budget is a necessary-but-not-sufficient lever.** 1200 is enough for the agent to *potentially* reach M6, but whether it does depends on planner noise + procedure-cache behaviour.

**Bigger picture:** the cross-game baselines collected the same week (mario 58 consecutive 8.20% death episodes, 2048 84% of decisions from 1 of 4 procs) showed that **the procedure cache itself has universal pathologies** — poisoning, dominance lock-in, futile loops. Those pathologies are what the next-generation MVA/TGAER architecture (Memory4 + Reflector + universal pathology guards) addresses. See [`docs/generalized-agent-mva.md`](../../generalized-agent-mva.md) on `docs/architecture-snapshot` branch.

## Next move (revised by v3 + v4)

1. **Commit `max_steps: 1200`** as the new production baseline. v3 showed it's enough to reach M6 in good runs; v4 showed extending to 2000 doesn't help. 1200 is the sweet spot.
2. **Step-budget lever is exhausted at this surface.** Tier 1 of the [TGAER roadmap](../../generalized-agent-mva.md) (per-skill success-rate floor + stagnation→demote + futile-action detector) is the right next bet — addresses the cross-game pathologies that v4's variance surfaced.
3. **GEPA on planner prompt remains a Tier 3 option**, but the priority shifted: cross-game pathology guards land first because they apply to mario + 2048 + pokemon simultaneously.

This PR closes the openevolve scaffold-search experiment cleanly. Verdict locked. Production default lands as part of merge.

## How to reproduce

```bash
# 1. Bootstrap a worktree with ROM + pokered repo symlinks (these are gitignored,
#    so `git worktree add` doesn't copy them)
git worktree add /workspace/orak-stage-s-evolve feat/openevolve-milestones-spike
ln -s /workspace/orak-stage-s/executables/pokemon_red/pyboy/pokered.gbc \
      /workspace/orak-stage-s-evolve/executables/pokemon_red/pyboy/pokered.gbc
ln -s /workspace/orak-stage-s/evaluation_utils/mcp_game_servers/pokemon_red/game/pokered \
      /workspace/orak-stage-s-evolve/evaluation_utils/mcp_game_servers/pokemon_red/game/pokered

# 2. Copy .env (has GEMINI_API_KEY + WANDB_API_KEY)
cp /workspace/orak-2025-starter-kit/.env /workspace/orak-stage-s-evolve/.env

# 3. Install openevolve
cd /workspace/orak-stage-s-evolve
VIRTUAL_ENV=/workspace/orak-stage-l/.venv uv pip install openevolve

# 4. Launch as PPID=1 daemon (8h overnight)
set -a && source .env && set +a
ts=$(date -u +%Y%m%dT%H%M%SZ)
setsid nohup /workspace/orak-stage-l/.venv/bin/openevolve-run \
    experiments/openevolve_milestones/initial_program.py \
    experiments/openevolve_milestones/evaluator.py \
    --config experiments/openevolve_milestones/config.yaml \
    --iterations 12 \
    --output experiments/openevolve_milestones/evolve_output \
    </dev/null >>logs/openevolve_real_${ts}.log 2>&1 & disown

# 5. Extract sweep aggregates (mean, std, scores) — append to the
# canonical pokemon_progression.yaml then regenerate the cross-stage
# bar chart with error bars (via autoresearch.plot_milestone_bars):
uv run python experiments/openevolve_milestones/extract_results.py \
    --log experiments/openevolve_milestones/evolve_output/logs/openevolve_<ts>.log \
    --rollouts /workspace/orak-evolve-rollouts/pokemon_red \
    --out experiments/openevolve_milestones/results.jsonl
# Hand-add an entry to experiments/milestones/pokemon_progression.yaml with
# the mean/std/scores fields, then:
uv run python experiments/plot_pokemon_progression.py
```
